# 过程留存机制（项目内部工作规范）

> **性质**：本文件是项目内部执行规范，**不是官方条款**。官方要求见 `findings.md` 第 4 节「提交物与完成标准」。
> **生效时间**：2026-11-09，从第一行业务代码之前生效。
> **为什么现在就建**：交接第 9 节明确「过程证据不可事后补」——细粒度 Git、Prompt 链、本人录屏必须从开发第一天同步留存；评分「过程可复现性与演进链路」占 25%。AI 能生成代码与文档，但代劳不了过程证据。

## 1. Git 细粒度提交

- 禁止一次性提交（`initial commit` 即含全部功能）——官方明文禁止。
- 每次提交 = 一次与 AI 的核心对话，或一个功能模块落地。
- message 格式：`<type>: <本次意图> (prompt: P-xxx)`；`type` 取 `docs / feat / fix / refactor / test / chore`。
- 每次提交后在 `evidence/devlog.md` 追加一行：时间、commit hash、意图、对应 Prompt 链编号、验收结果。
- 阶段 0 首次提交只允许含文档骨架，不含业务代码。

## 2. Prompt 链快照（官方：≥3 条完整链路，须含「引导 AI 修复 Bug」环节）

文件命名：`evidence/prompts/P-001.md`、`P-002.md`……，一条核心功能迭代一个文件。模板：

```
# P-xxx <功能名>
- 时间：
- 工具 / 模型：
- 对应 commit：
- 关联需求 / 痛点：

## 意图（我要 AI 做什么）

## Prompt 原文

## AI 的修改建议 / 生成内容

## 我如何引导 AI 修 Bug   ← 必填，官方明确要求

## 最终结果 / 验收

## 截图或录屏片段位置
```

- 至少 3 条，且至少 1 条含「引导 AI 修 Bug」的完整往返。
- 开发当天记录，禁止事后凭回忆补写。
- 工具不支持导出对话历史时，用截图或录屏留存，并在文件里注明采集方式（官方允许）。

## 3. 开发日志

`evidence/devlog.md`：每次提交一行，字段为 时间 / commit / 意图 / Prompt 链 / 结果。

## 4. 录屏清单（官方：5—8 分钟 MP4 1080p，其中 ≥2 分钟 AI 协同过程复现）

- [ ] 开场：真实痛点与用户场景
- [ ] 功能演示：核心链路走通
- [ ] AI 协同过程复现 ≥2 分钟：现场给 Prompt → AI 生成/修改 → 引导修 Bug → 提交
- [ ] 10 分钟极速复现指南演示
- [ ] 收尾：架构与可复现性说明
- 素材从开发第一天开始录，放 `evidence/screenshots/`；大文件默认不入库（见 `.gitignore`），按需单独加入。

## 5. 敏感信息（内部规范；官方明文要求待确认，见 `CONFIRM.md` B3）

- 所有 API key / token 走环境变量，`.env` 不入库；`.env.example` 在技术选型确定后建立。
- 仓库设为 Public 前执行密钥检查（`git grep` 常见 key 形式）与依赖清单核对。
- 公开仓库须含 README（官方要求）。

## 6. 目录约定

```
evidence/
  README.md        本文件
  devlog.md        提交级日志
  prompts/         P-xxx.md（写第一条链时创建）
  screenshots/     过程截图与录屏素材（默认不入库）
```

## 7. 与评分的对应

| 本机制产出 | 对应评分维度 |
|---|---|
| 细粒度 Git 历史 + devlog + Prompt 链 + 协同录屏 | 过程可复现性与演进链路 25% |
| Prompt 链中的意图与约束、修 Bug 引导 | 方法创新性与意图控制 20% |
| README 10 分钟复现、技术文档架构设计 | 工程质量与架构设计 15% |
